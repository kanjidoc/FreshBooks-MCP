## 1. What changed upstream

MCP `2026-07-28` converts MCP from a stateful, bidirectional protocol into a stateless
request/response protocol. What touches a stdio server like this one:

- **No handshake, no sessions.** `initialize` / `notifications/initialized` are gone. Each
  request carries its protocol version, identity, and capabilities in `_meta`. Servers
  **MUST** implement a `server/discover` RPC; on stdio it doubles as the client's
  era-detection probe.
- **`serverInfo` moved** to `_meta['io.modelcontextprotocol/serverInfo']`, stamped on every
  response instead of returned from a handshake.
- **Servers can no longer call back into clients.** Sampling, elicitation, and roots are
  replaced by Multi Round-Trip Requests (MRTR): the server returns
  `resultType: "input_required"` with `inputRequests`; the client retries the original
  request with `inputResponses`. All results now carry `resultType`.
- **List results become cacheable.** `tools/list` and friends return `ttlMs` and
  `cacheScope`; tools **SHOULD** come back in deterministic order.
- **Deprecated, 12-month minimum window:** Roots, Sampling, Logging, HTTP+SSE transport,
  Dynamic Client Registration. **Removed outright:** `ping`, `logging/setLevel`,
  `notifications/roots/list_changed`, SSE resumability, `resources/subscribe`.
- **Error codes moved:** resource-not-found `-32002` → `-32602`; `-32020`–`-32099` reserved.

### The compatibility rule that decides urgency

Implementations are **legacy** (`initialize` handshake; `2025-11-25` and earlier),
**modern** (`2026-07-28`+), or **dual-era**. **This server is legacy.**

The intake briefing carried a 4-row summary of the era matrix. The spec's actual matrix has
seven rows, and the rows it omitted change the shape of the decision:

| Client | Server | Outcome |
|---|---|---|
| Legacy | Legacy | **Works** — today's situation |
| Legacy | Dual-era | **Works** — server answers `initialize` |
| Legacy | **Modern** | **FAILS** — "Legacy clients have no fall-forward mechanism" |
| Dual-era | Legacy | **Works** — probe falls back to `initialize` |
| Dual-era | Modern | Works |
| Modern | Legacy | **FAILS** — no fallback exists |
| Modern | Modern | Works |

**The target is dual-era, not modern.** A modern-only server breaks every client in use
today (§4). This is the single most important correction to the intake briefing: it framed
the choice as "legacy vs modern," which quietly implies a cutover. The spec's own row —
*Legacy client → Modern server = Fails* — means a naive "migrate to v2" that lands
modern-only is a **breaking change for every existing install**, not an upgrade.

**Why this repo keeps working today.** On stdio a dual-era client probes with
`server/discover` and falls back "on any error that is not a recognized modern error." This
server answers an unknown method with a plain JSON-RPC method-not-found, which is not a
recognized modern error — so the fallback path engages and the client speaks legacy. The
risk is therefore *entirely* about when clients stop being dual-era.

> Source: <https://modelcontextprotocol.io/specification/2026-07-28/basic/lifecycle>
> (§ Backward Compatibility with Initialization-Based Versions, and the Compatibility Matrix)

### SDK situation

The TypeScript SDK did not version — it **split**.

- **v1:** `@modelcontextprotocol/sdk`, maintenance-only, npm `latest` = **`1.30.0`**.
- **v2:** `@modelcontextprotocol/server`, `/client`, `/core` at **`2.0.0`**. Declares
  `engines.node >= 20`. Requires Zod ≥ 4.2.0. **Ships both ESM and CJS** — verified, see §2.
- **Codemod:** `npx @modelcontextprotocol/codemod@latest v1-to-v2 .`, then
  `grep -rn '@mcp-codemod-error' .`
- **API shape:** `server.tool(...)` → `server.registerTool(name, {description, inputSchema}, handler)`;
  `extra` → `ctx`; Zod `*Schema` constants move to `@modelcontextprotocol/core`;
  `McpError` → `ProtocolError`; stdio served via `serveStdio(server)` from
  `@modelcontextprotocol/server/stdio`.

### Inherited claims that FAILED verification — do not carry forward

Both were stated flatly in the intake briefing. Neither is supported by the source it cited.
Both are load-bearing for risk assessment, so they are called out rather than quietly dropped.

1. **"A v2 server automatically serves legacy clients. Migrating is not a cutover."**
   **UNVERIFIED.** The v1→v2 upgrade guide does not state this. It says only that during a
   staged migration v1 and v2 "settle on the newest revision both packages support
   (currently 2025-11-25)." The release post does not address it either. Whether a v2 server
   is dual-era **by default**, by opt-in, or not at all is *unknown* — and per §1 it is the
   difference between an upgrade and a breaking change. **Resolve this before any plan is
   written.**
2. **"v1 bug and security fixes guaranteed for at least six months after v2's release
   (≈ late January 2027)."** **UNVERIFIED.** Neither the upgrade guide nor the release post
   states a v1 maintenance window. The confirmed 12-month figure is the *feature deprecation*
   window, which is a different thing. Do not use "we have until January 2027" as a planning
   input until it is sourced.

## 3. §3.1 ANSWERED — the Agent SDK is still v1-bound

**Yes, hard-bound — by declared peer dependency, which is stronger than the type imports
the briefing rested on.** Verified against the published tarball of
`@anthropic-ai/claude-agent-sdk@0.3.226` (npm `latest`) on 2026-08-09.

```json
"peerDependencies": {
  "@anthropic-ai/sdk": ">=0.93.0",
  "@modelcontextprotocol/sdk": "^1.29.0",
  "zod": "^4.0.0"
}
```

MCP v2 is **not a newer version of `@modelcontextprotocol/sdk`** — it is a different set of
packages (`@modelcontextprotocol/server`, `/client`, `/core`). A caret range on `^1.29.0` can
never resolve to any of them. **There is no version bump that gets you there.**

The typings agree. `sdk.d.ts` still imports `McpServer` from
`@modelcontextprotocol/sdk/server/mcp.js`, and:

```ts
// sdk.d.ts:482
export declare function createSdkMcpServer(_options: CreateSdkMcpServerOptions): McpSdkServerConfigWithInstance;
// sdk.d.ts:1061
export declare type McpSdkServerConfigWithInstance = McpSdkServerConfig & { instance: McpServer };
```

The coupling **did not loosen at all** between `0.2.97` and `0.3.226` — roughly 130 releases.
There is no signal that it is about to.

Reproduce:

```bash
npm pack @anthropic-ai/claude-agent-sdk@latest
tar -xzf anthropic-ai-claude-agent-sdk-*.tgz
grep -n "modelcontextprotocol" package/sdk.d.ts
node -p "JSON.stringify(require('./package/package.json').peerDependencies,null,2)"
```

**Scope note:** the coupling is specifically the **server-construction** path. The Agent
SDK's `tool()` helper produces tool-definition objects typed against v1's `CallToolResult`
and `ToolAnnotations`. How much of that survives a move to `registerTool` is a **separate,
unscoped question** — do not assume it is either trivial or total.

> Cross-repo: this question was answered once, centrally, for three repos.
> Full evidence: `~/Documents/Cursor/artifacts/answer-agent-sdk-v1-coupling.md`.

### Incidental: a latent peer-range trap

The Agent SDK peer requires `@modelcontextprotocol/sdk ^1.29.0`. This repo **declares**
`^1.27.1` — whose floor does **not** satisfy that peer (`1.27.1` ✗, `1.28.0` ✗).

**This is not broken today:** the lockfile pins `1.29.0`, which does satisfy it. It is
manifest hygiene — a trap for a fresh resolve or a deliberate downgrade, not a live fault.
If the Agent SDK is ever bumped toward `0.3.x`, the MCP SDK floor must rise to `≥1.29.0` in
the same change. Do it as **one coordinated dependency move**, not two.

installs break — not just this machine's.** That is what makes the trigger below worth
actively watching rather than assuming.

## 5. Open decisions — NOT decided here

These are the owner's calls. They are recorded as open, deliberately.

1. **Wait, or decouple?** With the Agent SDK v1-bound and no signal it will move, "wait for
   the Agent SDK" has **no end date**. The two real options:
   - **(a) Stay on v1 with a watched trigger** (§6). Cheap. The cost of being late is a
     broken local connection, not an outage.
   - **(b) Drop `createSdkMcpServer`** and build on `@modelcontextprotocol/server` directly.
     The only path to v2 that does not depend on someone else shipping. Touches the authoring
     pattern for all **97** tools, the `withAccount`/`withoutAccount` contract in
     `src/tool-registry.ts`, the `test/mcp-roundtrip.test.ts` harness, and the conventions
     documented in CLAUDE.md. **Architectural, not mechanical.**

   *Recommended default:* **(a)**, on the evidence in §4 — but this is a recommendation
   awaiting the owner's decision, not a decision.

2. **Consumer-facing release strategy** — open, and it must not be decided implicitly inside
   a dependency bump:
   - The **Node 20 floor** is a breaking change for consumers of a published package.
   - A protocol-era change is consumer-visible.
   - Does that make it a **major version** (`3.0.0`)? What does `CHANGELOG.md` say? Do older
     installs need a migration note?

3. **Do `ttlMs` / `cacheScope` and deterministic ordering earn their keep at 97 tools?**
   Unmeasured. Plausibly the largest manifest of any server here. Note: these are the
   protocol's answer to the *class* of problem behind the Claude Desktop stale-tool-list
   cache documented in CLAUDE.md — **they do not fix that existing bug and must not be sold
   as doing so.**

Revisit when **any** of these becomes true. This list is the whole point of choosing to wait.

- [ ] **A Claude client stops being dual-era.** The canonical check is §4's command — a
      `2026-07-28` entry appearing, or a legacy handshake failing, in
      `~/Library/Logs/Claude/mcp-server-freshbooks.log`.
- [ ] **The Claude Agent SDK drops or loosens its `@modelcontextprotocol/sdk ^1.x` peer
      dependency**, or ships a v2-based server constructor. Check with the §3 reproduce
      command; this single fact unblocks option (a).
- [ ] **A sunset date is announced** for legacy/dual-era client support.
- [ ] **A v1 SDK maintenance-window end date is published** (see §2, unverified claim #2).
- [ ] **A user reports a connection failure** attributable to protocol era.
